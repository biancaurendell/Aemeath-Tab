Codex 开发工作流地图

你的项目现在采用干净的新 main 主线。以后把 Codex 当成持久工作系统： 线程推进，文档记忆，Git 归档，验证器收口。

Aemeath Tab 主线：main 备份：archive/pre-history-reset-2026-05-24 原则：小步、可验、可回滚

一条主循环

input → context → plan → edit → verify → commit → memory
1

粗糙输入

把想法、截图、报错、现象丢给 Codex。不要追求一开始完美，先把问题说出来。

2

锁定边界

明确范围、不要做什么、验收标准。高风险任务先只读，不直接改。

3

最小改动

只碰当前任务需要的文件。避免顺手重构、顺手改样式、顺手清理旧东西。

4

验证器收口

构建、测试、浏览器检查、截图。没有 verifier 的任务不算真正完成。

5

提交与沉淀

只提交相关改动。把决策、踩坑、下一步写进项目文档，而不是只留在聊天里。

任务分流

不同任务，用不同闸门
BUGFIX

修 bug

先复现，再改动，再验证。不要把修 bug 变成视觉重做或架构优化。

FEATURE

加功能

先写用户路径和验收标准。功能完成后补入口、空状态、错误状态和设置项。

DEPLOY

部署目标

扩展版本走 WXT，网页版本走 Cloudflare。源码可同仓，构建产物不要进主线。

RISK

高风险操作

删文件、改配置、改远端、强推、部署，都必须先列计划和回滚方式。

修 Bug 模板

reproduce → isolate → patch → prove

给 Codex 的开工提示

任务：修复 [具体 bug]
现象：[截图/报错/复现步骤]
范围：只允许改 [模块/文件]
不要做：不要重构，不要改无关 UI
验收：
- 能复现旧问题
- 修复后旧问题消失
- pnpm build 通过
- 必要时浏览器检查桌面/移动

Codex 应该产出

  • 复现路径：哪一步触发 bug。
  • 根因：具体到函数、状态或样式规则。
  • 补丁：最小修改，不碰相邻无关代码。
  • 验证：命令结果和手动观察。
  • 提交：一个可回滚的 bugfix commit。

新功能模板

spec → slice → states → verify → commit

给 Codex 的开工提示

任务：增加 [功能名]
用户路径：
1. 用户从哪里进入
2. 点击/输入什么
3. 成功后看到什么
范围：只做第一版最小可用
不要做：不要顺手重构旧模块
验收：
- 主路径可用
- 空状态/加载/错误状态合理
- pnpm build 通过
- UI 不遮挡、不溢出

功能切片规则

  • 先做最小闭环，不先做豪华设置面板。
  • 先接入口，再接状态，再做边界。
  • 视觉跟随现有 Aemeath 风格，不另起一套设计语言。
  • 每个功能只进一个主题分支，完成后合回 main。
  • 功能完成后更新任务池或说明文档。

Git 车道

main clean, archive recoverable, feature disposable
main
干净主线只放完成且验证过的结果。
短历史方案 A 已压平为新根提交。
可部署扩展与 Cloudflare 源码都在这里。
少争论以后不把试错直接堆主线。
feature/*
单一任务一个 bug 或一个功能。
随时可扔失败实验不污染 main。
小提交每个小点可回滚。
完成合并必要时 squash 成漂亮提交。
archive/*
旧历史乱历史保留但日常不看。
查账用需要找旧代码时再切。
不开发不要在 archive 上继续写功能。
保险绳重建历史后仍可找回。

高风险闸门

read-only first, then plan, then execute
01

只读诊断

先看状态、配置、日志、diff。不能修改、不能删除、不能推送、不能部署。

02

列计划和回滚

明确将执行的命令、影响范围、失败后怎么还原。你确认后才进入执行。

03

小步执行

一次只做一个动作。每一步后检查状态，不把多个破坏性动作串成一条命令。
